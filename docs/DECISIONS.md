# Decisions

A running log of technical decisions and lessons, newest first.

## 2026-08-11 — Image generation moved to a free remote API; the abstraction earned its keep

Local image generation was abandoned the same day it went live. On a 24 GB machine the 12 GB model cannot coexist with the chat models: every draw evicted qwen3, a warm generation took 2–4 minutes, the runner panicked at the memory ceiling, and the model was removed at the user's request. The replacement is Pollinations.ai — a genuinely free, keyless image API (one GET, FLUX-backed, anonymous rate limit ~1 request/15 s, fine for a single user): a 768² image now arrives in ~2 seconds instead of minutes, with zero RAM cost. Measured end-to-end through the assistant: 28 s total including qwen3 load, tool call, and streamed answer. This is Cortex's one deliberate exception to local-first, and its boundary is worth stating: only the draw-prompt travels; documents, questions, and retrieval never leave the machine. The pivot touched exactly one provider file plus a config switch (`IMAGE_PROVIDER`), which is the abstraction rule doing precisely what it was written for — the Ollama implementation stays behind the same Protocol for a bigger machine, and the tool, graph, widget, and frontend never noticed the swap. One contract lesson: the first `GeneratedImage` carried a `png_base64` field, but Pollinations returns JPEG — the dataclass now carries raw bytes plus an extension, because a provider contract should never bake in one implementation's output format. Side effect: with the local path optional, the Ollama 0.32.5 pin matters only to whoever sets `IMAGE_PROVIDER=ollama`.

## 2026-08-11 — The experimental image runner is fragile exactly at the memory ceiling

First real-world session with `generate_image` surfaced two lessons. The bug report read "Tool error: The image model finished without returning an image" — but the Ollama server log told the real story: the experimental MLX image runner *panicked* inside the VAE decode (`index out of range` in `zimage/vae.go`, `mlx scanner error: unexpected EOF`), and the HTTP stream ended with status 200 and no image. Standalone, a 1024² generation succeeded every time; inside a chat turn it crashed — the difference is that qwen3 sits loaded next to the 12 GB image model, and generation peaked at 13.4 GB, which together with the OS lands exactly on this machine's 24 GB. The runner's failure mode at the ceiling is a panic, not an error message. Two changes: the provider now surfaces `error` lines from the stream instead of silently skipping them (the original code only looked for `image`, so Ollama's dying words went unread — never parse a stream for only the happy-path field), and the default `image_size` dropped 1024 → 768, which cuts VAE and per-step memory roughly in half and takes a warm generation from ~4 to ~2 minutes. Worth recording on the credit side: LangGraph's model ⇄ tools cycle retried the failed tool on its own — three later rounds generated and saved images with no code asking for it — and the panic was diagnosed entirely from `/opt/homebrew/var/log/ollama.log`, which is the first place to look when a tool "returns nothing."

## 2026-08-10 — Image generation through Ollama's experimental API

The assistant can now draw: a `generate_image` tool turns "draw me…" requests into a detailed prompt, and the result renders as an image card widget like any other. The provider decision was the easy part: Ollama 0.32.5 ships experimental image generation through the same `/api/generate` endpoint the LLM provider already talks to, so `ImageGenerator` → `OllamaImageGenerator` is one new file following the exact pattern of the other nine providers — ComfyUI (most controllable) and Draw Things (fastest on Apple Silicon) were considered and rejected because both mean running and babysitting a second inference server for a capability the already-running one now has. The model is `x/z-image-turbo` (6B, Apache 2.0). One operational constraint worth recording: the image API was temporarily removed in later Ollama releases, so Ollama stays pinned to 0.32.5 until it returns — the abstraction is the insurance policy if it never does. Storage was the real decision: widgets persist as JSONB on the message, but a 1024² PNG is 1–2 MB, and inlining it as base64 would bloat every conversation fetch and SSE replay forever. Instead the PNG lands on disk under `backend/generated_images/` (gitignored), a static mount serves it at `/images/{filename}`, and the widget stores only the filename — the browser caches the file, the database stays light, and orphaned files on conversation delete are an accepted cost for a single-user tool. The surprise came from the router: adding "asks to generate, draw, or create an image or picture" to the middle of the route prompt's no-list flipped two unrelated small-talk cases at temperature 0 — a 4B classifier is sensitive to clause *position* in a long instruction sentence, apparently because what sits between the list and its trailing "or is small talk" examples dilutes them. Measured A/B on the failing cases, moved the clause to the end of the list, and the grown set (42 questions, four image cases including a follow-up) is back at 100%. Lesson: in prompts for small models, where an instruction sits is part of the instruction — and only the eval catches the regression a harmless-looking edit causes three clauses away.

## 2026-08-10 — Branching: a conversation fork is a deep copy, not a reference

Any assistant answer can now branch the conversation into a new chat — a full copy of everything up to that answer, opened immediately, with a divider at the copy point naming the source ("Branched from ⟨title⟩", clickable). Copy-versus-reference was the real decision: sharing message rows between conversations would save space but poison everything built on top — feedback sits on messages, ids anchor citations and steps, and an edit-through would mutate history in two places. A deep copy costs a few rows and keeps every existing feature correct by construction; the copied messages get fresh ids, so votes and future branches in the fork are independent. Three details earned their thought: the branch stores `branched_count` alongside `branched_from_id`, because the divider must stay pinned at the historical copy point while the branch grows past it; the source link is a self-FK with `ON DELETE SET NULL`, so deleting the original never blocks and the branch just shows "a deleted chat"; and the conversation summary copies over only when the whole summarized region lies inside the copied prefix — branch early enough and the summary would describe messages the branch doesn't contain, so it is dropped and rebuilds naturally. Feedback votes deliberately do not copy: a vote belongs to the answer the user actually rated, and copying would double-count the dashboard. The feature cost one endpoint and ~40 frontend lines because the `saved` event from the feedback work already gave every rendered answer its message id — infrastructure paying out one feature later, same as chunk metadata did for citations.

## 2026-08-10 — Answer feedback: votes are edits, not commitments

Every assistant answer now takes a like or dislike. The model is one nullable `feedback` column on `messages` — a message has at most one current vote, so a column is the honest shape, and because conversations already return their messages with steps, sources, and widgets, persistence and replay came free. The first build made votes immutable per the original spec (a conditional `UPDATE … WHERE feedback IS NULL`, second attempt 409) and it was reversed the same day, before shipping: immutability protects signal purity against many users gaming a metric, but for a single-user local tool it only punishes mis-taps and changed minds — the whole accidental-tap UX problem existed *because* of irreversibility, and disappeared with it. Now `PUT /messages/{id}/feedback` is an idempotent set: same value again clears it, the other value switches, last state wins. The feature exposed a real gap either way: the frontend had no message ids, because the assistant message persists *after* the `done` event (summarization may run an LLM call there, and `done` must not wait for it). Fix: `save_exchange` was split from summarization — persistence now happens before `done` and a `saved` event streams the new message id, summarization stays after. Side effect worth having: an answer is now guaranteed durable before the client is told the run finished. UX: the thumbs sit in the muted usage row under the answer, which only renders once a message is complete and has an id — so streaming messages can't be voted on by construction; the active thumb fills (green/red) and tapping it again empties it. Dashboard shows plain Liked/Disliked counts — no satisfaction percentage until the denominator means something. The quiet payoff: every dislike is a flagged real-world failure, and flagged failures are golden-set candidates — the feedback loop exists to feed the eval loop. Lesson, same as the API keys: a guarantee is only worth its constraint when the threat it defends against actually exists.

## 2026-08-10 — The router learned to see follow-ups

A per-message classifier is conversation-blind: "And for silver?" carries no topic of its own, so the router judged it in a vacuum even though the previous turn ("What is the current price of gold?") settles the routing completely. Fix: `decide_route` now receives the previous user question and the route prompt frames the message as "… (follow-up to: <previous>)", truncated to 200 characters so a long earlier turn cannot crowd out the message actually being judged. The golden set gained follow-up cases in both directions — "And how about black tea?" after a notes question must still reach documents, "And for silver?" after a price question must not — and grew to 38 questions. Measured: 38/38 = 100%, zero misses in either direction, ~700 ms average routing latency. Lesson: any single-message classifier sitting inside a conversation needs its context threaded in explicitly, and every context rule needs golden cases in both directions or the fix can silently trade one error family for another.

## 2026-08-10 — Tool results grew visual cards

Tools can now return a widget besides their text: `ToolOutput` carries an optional `Widget` (kind + data), the tools node streams it as a `widget` event, a reducer field accumulates widgets in graph state, and they persist as JSONB on the assistant message next to steps and sources — so reopened chats replay their cards the same way they replay traces and citations. Four cards come from the outside world: `world_clock` (superseding `current_time`, IANA-timezone-aware, defaulting to the user's timezone), `get_weather` behind a `WeatherProvider` (Open-Meteo, keyless), and `crypto_price` behind a `MarketDataProvider` (CoinGecko, keyless) whose raw 24h series is thinned to at most 72 points before it touches state or the stream. Two more let Cortex answer questions about itself — `kb_stats` (documents, chunks, collections, conversations) and `usage_stats` (7-day prompts, tokens, average latency) query Postgres directly, reusing the logs kept since step 3. The text and the widget carry the same facts on purpose: the text is what the model reads, the card is what the user sees, and the system prompt tells the model to answer in one short sentence beside a card and never repeat its numbers in a list or table — the card, not the transcript, is the presentation layer. The routing set gained stats questions so "How many documents are in my library?" skips document search and goes straight to the tool.

## 2026-08-09 — Mermaid diagrams: a renderer the model must be told about

Answers can now carry mermaid code blocks; the frontend lazy-loads mermaid (main bundle unchanged, the diagram machinery arrives as separate chunks on first use), renders them to SVG with a download button, and falls back to the raw code while streaming or on invalid syntax. The first live test produced "Ranking flowchart (textual): 1 → 2 → 3" — the renderer existed but nothing told the model, so the system prompt now advertises the capability. Two more rules earned by testing: node labels must be double-quoted (unquoted parentheses inside labels are a mermaid parse error the fallback would silently swallow), and a message that already contains everything needed to answer must not enter the search cascade — one run tried to web-search "how to draw a flowchart" it had full instructions for. Lesson: a capability the model cannot see does not exist; every renderer needs a prompt-side advertisement, and every format rule needs a 4B model's syntax pitfalls spelled out.

## 2026-08-09 — The model gets today's date in the system prompt

Two web-search answers called Aug 2026 "a future date, which may be an error" — qwen3 believes its training-cutoff year is the present, and nothing corrected it (the `current_time` tool exists, but the model saw no reason to call it before doubting a date). The system message now ends with "Today is <weekday, month day, year>", built per run so a long-lived server never staples a stale date into fresh conversations. Lesson: a frozen-clock model treats every post-cutoff date as suspicious; the current date is context the model cannot be trusted to fetch for itself.

## 2026-08-09 — Phantom citations on unsourced runs

"tell me a joke" came back with a trailing [1] — the run had no search, no sources, nothing to cite; the standing citation instructions pattern-matched the 4B model into decorating the answer anyway (the frontend chip guard correctly refused to link it, leaving inert text). Two-layer fix: the system prompt now states outright that no search results means no bracketed numbers, and `final_answer` strips unmatched markers when the run's source registry is empty — sourced runs are untouched, so real citations cannot be collateral damage. Accepted trade-off: an unsourced answer discussing bracket syntax as literal text would lose it. Verified both directions: the joke persists clean, an espresso question keeps its [1]. Same lesson as the invented web-citation ids: a small model will emit whatever format the prompt teaches, so every format rule needs an enforcement path outside the model. Verification also surfaced a wart worth remembering: explicitly-passed None in the JSONB columns persists as JSON null rather than SQL NULL, so `IS NOT NULL` checks on `messages.steps`/`sources` lie.

## 2026-08-09 — The router was gambling: classifier calls now run at temperature 0

A screenshot of "Reply with just the word hi." running a document search first exposed two problems. The obvious one: the few-shot route prompt covered greetings ("hey there") but not imperative small talk — messages that tell the model what to say back read as tasks, and the prompt's deliberate yes-bias sent the whole family to retrieval, where the empty result then cascaded into an absurd web-search approval prompt ("results empty → search more → then web" is right for real questions, nonsense for greetings). The subtle one: `complete()` never pinned temperature, so every routing decision sampled at Ollama's default — plain "hi", correct when the router was first measured, had drifted back to "yes"; the 96% was an estimate of a moving target. Fixed in the house order: six new golden cases first (four imperative small-talk, two protective imperative look-alikes that do need documents, like "Tell me what my notes say about coffee brewing"), baseline 87% with all four misses in the harmless direction, then temperature 0 on all `complete()` calls, one rule clause ("messages that just tell you what to say back"), and two few-shot examples — 100% on 30 questions, zero misses either way, latency unchanged. A system-prompt guard (small talk is answered directly, never searched) closes the cascade for anything that still slips through. Lessons: a classifier must be deterministic before its accuracy number means anything, and every error found in the wild joins the golden set before it gets fixed.

## 2026-08-09 — Wall clock joined usage, timed per node

The usage line under answers now leads with response time. Rather than timing the HTTP stream — which covers only the final segment of an approval-interrupted run and would count the minutes a user stares at the Allow button — every graph node is wrapped in a `timed()` decorator that adds its own duration to an `elapsed_ms` reducer field in state. Same pattern as tokens: segments sum across interrupts, checkpoints carry it through crash recovery, and the pause between `interrupt()` and resume costs nothing because no node is running. One known blind spot, accepted: a node killed mid-flight re-executes on resume and only the successful attempt is counted. `prompt_logs.latency_ms` keeps its original per-segment meaning for dashboard continuity.

## 2026-08-09 — Token counts restored, accumulated in graph state

When Ask folded into the assistant, token counts were "dropped for now": the old `/ask` path read Ollama's `prompt_eval_count`/`eval_count` from `stream()`, but the assistant answers through `chat_stream`, which discarded them — the dashboard token tiles have silently read 0 since. Restored end to end: `chat_stream` captures the counts from the final chunk into `ChatReply`, and the model node adds them to two reducer fields in graph state (`operator.add`), which sums them across tool-loop rounds and — because state checkpoints to Postgres — carries them through approval interrupts and crash recovery with no extra bookkeeping. A completed run emits a `usage` SSE event before `done`; the totals persist to `prompt_logs` and onto the assistant message, so reopened chats show usage the same way they replay steps and citations, rendered as a muted line under the answer. Verified on a run that paused for web-search approval and resumed: both model rounds summed correctly across the two HTTP requests. Two honest numbers to know when reading it: response tokens include qwen3's discarded thinking (the visible answer is a fraction of the compute), and the counts cover the answering model only — route, title, and summary calls are excluded as bookkeeping. Lesson: usage belongs in run state, not request scope — the same argument that put the citation registry there.

## 2026-08-08 — Run state must not outlive its conversation

A chat paused on web-search approval locked the composer in every other chat, including new ones. Root cause: `busy` and the awaiting-approval flag are view-level state shared by all conversations, and the route-change handler reset messages but not them — the lock leaked across chats. The fix leans on the crash-recovery design instead of adding state machinery: switching conversations now aborts the in-flight stream (AbortController through every fetch) and clears the run flags. An aborted stream is indistinguishable from a crash on the server — the run stays checkpointed under its `active_thread`, so returning to that chat auto-continues it, and a pending approval card simply re-emerges from the re-raised interrupt. This also closed the nastier sibling bug: an uncancelled stream's handlers kept writing to "the last message" after a switch, which would have appended chat A's tokens into chat B's bubble. Two guards matter: the route effect only aborts when the route actually differs from the current conversation (otherwise adopting a newly created chat would abort its own first stream), and each stream's cleanup checks its own abort signal so a dying stream can't flip `busy` under the next one.

## 2026-08-08 — A measured router decides when to skip document search

"Search the web: what's the Bitcoin price?" still ran the seeded document search first — harmless (the relevance gate emptied it) but wasteful and noisy in the trace. Fix: a `route` node at the graph entry asks gemma3:4b one question — does this message need the user's documents? — and a conditional edge either runs the seeded `retrieve` or jumps straight to the model. Router cost ~460 ms, roughly what the skipped search costs, so latency nets out; the win is an honest trace. Per the house rule, the router was measured before being trusted: a 24-question routing golden set (`evals/routing.py`). First prompt scored 79% with two errors in the dangerous direction (document questions routed away from grounding — a false "no" silently un-grounds an answer, while a false "yes" just wastes a search). Rewriting the rules-only prompt into a few-shot prompt with eight labeled examples moved it to 96% with zero dangerous misses; the one remaining error routes "hi" to documents, the harmless direction. Lesson twice over: small models classify far better from examples than from rules, and an asymmetric-cost decision needs its error directions reported separately — a single accuracy number would have hidden exactly the failures that matter.

## 2026-08-08 — Web results joined the citation registry

First real answer with a web claim exposed a hallucinated citation: "$63,709.78 USD [5]" where no source 5 existed — document chunks were numbered but web results were an unnumbered text blob, so the model invented a plausible-looking id (and the frontend, correctly, refused to render it as a chip). Fix: web results register in the same state-held sources registry as document chunks, with their URLs; the tool result the model reads shows `[n] title / url / snippet`, and the source card in the UI links out to the page. Retested: five numbered web sources, answer cited [2], chip resolves to the exact page the price came from. Lesson: a citation scheme must cover every evidence channel the model sees, or the model will improvise numbers for the uncovered one.

## 2026-08-08 — Citations and crash-proof streams

Two features cashed in infrastructure that already existed. **Citations:** chunk metadata stored since day one finally pays off — every retrieved passage gets a global number (`[1] coffee.md`), the model is instructed to cite passage numbers after claims, and the frontend turns `[n]` markers into clickable chips that expand the exact source chunk. The numbering registry lives in graph state (not request scope) deliberately: an approval interrupt splits one run across two HTTP requests, and a request-scoped counter would restart at [1] and mis-map every earlier citation. qwen3:4b followed the citation instruction on the first try once passages carried visible numbers. **Stream resume:** the Postgres checkpointer already made runs durable; now the conversation row tracks its `active_thread`, and if the browser dies mid-answer, reopening the chat calls `/assistant/continue` — a `snapshot` event replays the question, steps, and sources from the checkpoint, then the graph re-runs from the last completed node and streams the rest. The interrupted node re-executes from its start (tokens may differ between attempts; tools re-run), which is the documented LangGraph trade-off for exactly-once-per-node checkpointing. A run killed before its first checkpoint returns 409 and clears the thread — that exchange is simply lost, which is honest. Verified by killing a live run at 20s and continuing it: the snapshot carried two steps, re-execution renumbered sources consistently, and the final answer persisted with citations intact.

## 2026-08-08 — Ask folded into the assistant: one conversation surface

The last tab split fell: `/ask` (the fixed RAG pipeline) merged into `/assistant` via an always-first `retrieve` node — the retrieval funnel runs with the raw question before the model's first turn, streamed and persisted as an ordinary `search_documents` step. Simple questions keep Ask's behavior (guaranteed grounding, one model turn, streamed answer); complex ones escalate into the tool loop. First test exposed a prompt bug: the raw comparative phrasing "Compare how coffee and tea are prepared" scored below the relevance gate, and the model jumped straight to `web_search`. One system-prompt change — "split into sub-topics and search documents again *before anything else*" — and the same question produced two focused searches hitting coffee.md and tea.docx, no web. Query rewriting for follow-ups was deleted with `/ask`: if the seeded search misses, the model re-searches with history in view, which is the same repair without a dedicated LLM call. Prompt logging moved to the assistant (transcript of steps as the logged prompt; token counts dropped for now). The chat collection filter was removed as unused friction — collections remain a document-organization feature. The eval harness still measures the retrieval funnel and `build_answer_prompt` directly, so retrieval changes stay measurable even though no endpoint runs that exact pipeline anymore.

## 2026-08-08 — Durable agent state and human-in-the-loop approval

The assistant graph now checkpoints to Postgres (`langgraph-checkpoint-postgres`): state is saved after every node under a per-request `thread_id`, which makes the run pausable and resumable across HTTP requests. On top of that sits the first human-in-the-loop gate: before executing `web_search`, the tools node calls `interrupt()` — the graph parks itself in the database, the SSE stream emits an `approval` event with the thread id and ends. `POST /assistant/resume` with `Command(resume=approved)` re-enters the node, `interrupt()` returns the decision, and the run continues (declined searches feed "the user declined" back to the model as the tool result). Approvals are gathered before any tool executes so a resume never re-runs a side effect. Two lessons paid for in debugging: psycopg's pool must be opened explicitly (`open=False` + `pool.open(wait=True)`) — the deprecated implicit open hung silently; and the checkpointer must be initialized at app startup, because lazy setup inside a request self-deadlocks — `CREATE INDEX CONCURRENTLY` waits for every open transaction, including the request's own SQLAlchemy session. Checkpoint rows accumulate per request; cleanup is deferred until it matters. Also observed: qwen3 sometimes answers post-cutoff questions from stale training knowledge instead of searching — model judgment, unlike the old hardcoded fallback, can be wrong in both directions.

## 2026-08-08 — Chat and Agent merged into one streaming Assistant

The tool-calling Chat and the plan-based Agent solved the same problem with opposite control flow: model-driven versus code-driven. Both are now one `/assistant` endpoint — a two-node LangGraph cycle (`model ⇄ tools`) where the model orchestrates itself, streaming every step over SSE (`tool_call`, `tool_result`, `token`, `title`). The open question was whether a 4B model could carry the orchestration the hardcoded planner guaranteed. Measured: "Compare how coffee and tea are prepared" produced two focused `search_documents` calls in one turn, each hitting the right file; the World Cup question skipped documents and answered from one `web_search` — where the workflow agent had burned four web searches and 136s on the same question. The relevance gate moved into the `search_documents` tool itself, so "no relevant documents" becomes something the model sees and reacts to. Tool steps persist as JSONB on the assistant message, so reopening a chat replays the trace. Both old endpoints and the Phase-A workflow graph are deleted; prompting a capable loop replaced hardcoded decomposition.

## 2026-08-08 — Agent rebuilt on LangGraph, retrieval fan-out parallelized

The hand-rolled planner → retriever → reasoner pipeline was rewritten as a LangGraph `StateGraph`: a `plan` node, a `Send` fan-out that runs one `retrieve` node per search query in parallel, and a `reason` node that deduplicates and synthesizes. LangGraph orchestrates only the control flow — every node still calls our own `LLMProvider`, retrieval funnel, and `WebSearchProvider`; no langchain model wrappers entered the project. Head-to-head on the same questions, answers were equally correct and the graph was faster because retrieval fans out in parallel: coffee-vs-tea 55.9s → 48.4s, World Cup (web fallback) 136.3s → 118.5s. The sequential pipeline is deleted; its dedup moved after the fan-in, since parallel steps can no longer see each other's chunks mid-flight. Side observation: plan phrasing drives relevance-gate hits — "step-by-step coffee brewing methods" scored below the gate against coffee.md while "How coffee is prepared" cleared it, so identical questions can route to web or documents depending on how the 4B model words its plan.

## 2026-08-06 — Web search fallback needs a relevance gate

Added free web search (ddgs/DuckDuckGo, no API key) behind a `WebSearchProvider` abstraction: a `web_search` tool in chat mode, and a fallback in the agent when documents have nothing. First attempt never triggered — vector search has no concept of "no relevant results"; it always returns the nearest chunks, so findings were never empty. Fix: the cross-encoder already scores every candidate, and irrelevant pairs score below zero, so the agent now filters evidence by rerank score (`agent_min_relevance`, default 0.0) and falls back to the web only when nothing relevant survives. Lesson: "top-k" is not "relevant-k" — thresholds must come from a model that actually measures relevance. Web snippets are shallow evidence; fetching full pages for top results is the known upgrade.

## 2026-08-06 — API keys removed after being built

Step 15 added API key auth (SHA-256 hashed at rest) and per-key rate limiting. Both worked, and both were removed the same day: for a single-user tool running on localhost, pasting a key into your own frontend is pure friction with no threat model behind it. The lesson kept: auth design (hash keys, meter usage per identity) and the discipline of removing features that don't pay their way. The git history preserves the implementation for when deployment or multi-user support makes it relevant.

## 2026-08-06 — Cross-encoder re-ranking measured

Funnel: hybrid retrieval fetches top-30 candidates, `cross-encoder/ms-marco-MiniLM-L-6-v2` re-scores them, top-5 survive. Measured on 29 golden questions:

| Mode | hit@1 | MRR | avg retrieval |
| --- | --- | --- | --- |
| hybrid only | 25/29 = 86% | 0.925 | 61 ms |
| hybrid + rerank | 29/29 = 100% | 1.000 | 227 ms |

hit rate@5 was already 100%, so the win shows in ranking quality: every answer now sits at position 1, meaning the LLM sees the best evidence first. Price: ~170 ms of local model inference per query. `RERANK=false` disables it. The cross-encoder runs inside the backend process via sentence-transformers — the first dependency that executes a neural network in-process instead of behind Ollama's API.

## 2026-08-06 — Hybrid search measured

Corpus at 29 golden questions over ~100 chunks (examples + crawled pages + the Cortex repo itself):

| Mode | hit rate@5 | avg retrieval |
| --- | --- | --- |
| vector only | 28/29 = 97% | 43 ms |
| hybrid (RRF) | 29/29 = 100% | 50 ms |

The rescued question was "What is the Great Red Spot?" — an exact phrase that full-text search finds at rank 1 while vector search had let it slip out of top-5 as the corpus grew. Two side lessons: eval scoring must normalize whitespace (pypdf wraps lines mid-phrase, which made a rank-1 hit look like a MISS), and `plainto_tsquery` ANDs all terms, so one absent word empties the keyword result — the vector leg covers those cases, which is exactly why hybrid works.

## 2026-08-06 — Schema migrations are not data migrations

Adding `content_hash` for duplicate detection looked done once the column migrated — but documents ingested before the migration had NULL hashes, so re-uploading one of them slipped past the duplicate check. Lesson: a new constraint only protects rows written after it; existing rows need a backfill (or, in dev, deletion and re-ingestion). The column stays nullable because the original text cannot be reconstructed from overlapping chunks.

## 2026-08-06 — Evaluation baseline

First eval run over 3 documents (6 chunks), 25 golden questions, qwen3:4b with thinking enabled:

| Metric | Value |
| --- | --- |
| hit rate@5 | 25/25 = 100% |
| answer accuracy | 25/25 = 100% |
| avg retrieval | 39 ms |
| avg generation | 7.6 s |

With only 6 chunks and top-5 retrieval, a perfect score is expected — the numbers become meaningful as the corpus grows. Every retrieval change from here on is judged by re-running `python -m evals.run`.

## 2026-08-06 — Run Qwen3 with thinking enabled

Qwen3 is a reasoning model. Disabling thinking (`think: false`) did not suppress it — reasoning leaked into the answer stream. Running it as designed (`think: true`) makes Ollama separate reasoning into a `thinking` field, which the LLM provider discards, streaming only the clean answer. Cost: a few seconds of silent thinking per answer. Benefit: better answers, clean output.

## 2026-08-06 — Qdrant instead of pgvector

Started with pgvector to keep everything in one database, then switched to Qdrant to learn a dedicated vector database from day one. Postgres remains the source of truth (documents, chunks, logs); Qdrant stores one vector per chunk keyed by chunk id. Keeping the two stores in sync is the ingestion service's job. Trade-off accepted: two systems instead of one, in exchange for hands-on experience with a real vector database. The `VectorStore` abstraction keeps the swap back cheap.
